# ゲームプレイコードのクラス分割 引き継ぎ

GamePlayScene に集中している処理を、関係ごとにクラスへ分けるコード作業用メモです。ゲーム概要や現時点の制作方針は [GAME_DESIGN_HANDOFF.md](GAME_DESIGN_HANDOFF.md) を参照してください。

## 目的

ゲームシーンにプレイヤー、敵、武器、採掘、HP、戦闘、描画などの処理が集まり、コードを追いにくくなっています。責任のまとまりごとにクラス化し、今後の武器追加・モーション・エフェクト実装を進めやすくします。

候補となるまとまり：

- **Player**：移動・ジャンプ、HP・被弾・死亡、現在の武器、プレイヤー表示や動作。
- **Enemy**：位置・移動・攻撃、HP・被弾・撃破、敵表示や動作。
- **Weapon**：種類ごとの性能、攻撃開始・攻撃時間・攻撃判定に関わる情報。
- **GamePlayScene**：フェーズとゲーム進行、各クラスへの指示、カメラ・UI・シーン遷移など。

これは責務を検討するための候補です。既存設計を読まずにこの構成をそのまま実装しないでください。特に武器の所有者、装備と所持品、採掘とTileMapの関係はコードを見てから提案してください。

## 実装前の確認（最初はコードを変更しない）

現在の `GamePlayScene.h/.cpp` を読み、状態変数、入力、更新、描画、勝敗、素材管理、演出、シーン遷移の関係を図または箇条書きで整理してください。既存の `BaseScene`、`TileMap`、`Object3d`、`AnimationClass`、`ParticleManager` 等の責務も確認してください。

次に、以下を説明してください。

- どの処理・データが現在 GamePlayScene に集中しているか。
- Player / Enemy / Weapon の境界をどこに置くか。
- 各クラスが保持・更新・描画する情報と、GamePlayScene に残す責務。
- インターフェースの案と、クラス間の依存関係。
- 既存挙動を変えずに分割する段階的な手順。
- 変更対象ファイル、想定リスク、ビルドや実機で確認すべき内容。
- 将来のハンマー・やり、攻撃モーション、エフェクトをどのクラスへ追加しやすくなるか。

**この確認段階ではコードを変更しないでください。** まず提案を示し、ユーザーが実装を依頼した後に、挙動を保つ小さな段階に分けて作業してください。大規模な一括書き換えや、根拠のない抽象基底クラス・汎用フレームワークの追加は避けてください。

## 進め方の方針

1. 分割前のゲーム挙動と操作を把握する。
2. Player、Enemy、Weapon の責任とデータ所有者を合意する。
3. まず一つのまとまりを移し、GamePlayScene から呼び出す形にする。
4. 変更のたびに既存ゲームループが維持されているか確認する。
5. 残りのまとまりを段階的に移し、武器追加に必要な窓口を明確にする。

武器やエフェクトの別チャットでコードを同時編集しないでください。先にクラス分割を行うか、武器を追加してから分割するかは、実際の依存範囲を調べて事前確認時に推奨順を提案してください。ユーザーが複数のコードチャットを同時に進める場合は、変更ファイルの競合を避けるため、担当範囲と順序を先に定めてください。

## 完成目安

- GamePlayScene のコード量だけを別ファイルへ移したのではなく、責任ごとに状態と処理の所有者が明確になっている。
- 作業・戦闘・死亡・勝敗・ボス・ゲームオーバー・ゲームクリアの既存進行が維持される。
- 採掘、素材数、武器作成、HP、敵HP、攻撃、HUD、入力の連携先が分かる。
- 次の武器・アニメーション・パーティクルをどこへ追加するか迷いにくい。
- コードが複雑化するだけの重複ラッパーや不要なクラスを作らない。
